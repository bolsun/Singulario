# T014 — Производительность, первый проход: замер, симуляция по событиям, отрисовка

Статус: выполнена (ветка `feature/perf-pass1`). Уточнения пользователя по ходу: вращатели и бросатели
заморожены (оставлены на своём списке, каждый тик, как раньше); из детализации — только ступень
«атом — точка цвета тира», заливка чанка по тиру — отдельной задачей.

Ветка: `feature/perf-pass1` от `experimental` (`git checkout -b feature/perf-pass1 experimental`).
После отчёта — влить в `experimental` (CLAUDE.md, «Процесс»). В `main` не пушить.
Контекст: `NucleusLayer.cs` — `SimTick` (шаги 1, 2 проходы A/B, 3 источники, вращатели),
`UpdateVisibleChunks`, `UpdateChunkVisuals`, `RebuildChunkMeshes`; режим случайного заполнения
(клавиша T, `RandomFillEnabled`). Словарь: «ядро» в дизайне = атом (в коде Nucleus/`NucleusEntity`).

## Проблема
Пользователь: игра «умирает» при паре десятков тысяч атомов (режим случайного заполнения).
Наблюдения по коду:
- каждый тик (60/с) все атомы обходятся 3–4 раза, у каждого 4 стороны через `Dictionary<(row,col)>`
  и `HashSet<(атом, слот)>`, хотя передача меняется только на тиках поворота (все периоды
  кратны 4 — на 3 тиках из 4 не поворачивается никто; Ж — раз в 32 тика);
- отрисовка: каждый кадр у каждого видимого атома ~17 вызовов `SetInstanceTransform2D`
  (корпус + 8 дырок + 8 частиц) — сотни тысяч обращений к движку за кадр;
- **детерминизм нарушен:** `_activeSet` — `HashSet<NucleusEntity>`, порядок обхода зависит от
  хеш-кодов объектов (меняются от запуска к запуску), а при споре за дырку побеждает тот, кто
  раньше в обходе.

## Что сделать (по шагам, после каждого — сборка и коммит)

### 1. Замер
- В HUD (включается клавишей, например F3): число атомов (всего / видимых), мс на тик
  симуляции (среднее и максимум за последнюю секунду), тиков за кадр, мс кадра / FPS,
  мс на обновление отрисовки атомов.
- Ничего долго не прогонять самому: пользователь проверит сам на случайном заполнении.
  Коротко убедиться, что счётчики показывают разумное.

### 2. Симуляция: фиксированный порядок и работа по событиям
- **Сначала — фиксированный порядок обхода** (например, по чанку, затем по клетке) вместо
  `HashSet`. Отдельный коммит: это меняет поведение в спорных случаях, но делает его
  детерминированным.
- **Затем — работа только по событиям**, с тем же результатом бит в бит, что у полного обхода
  с фиксированным порядком:
  - атомы разложены по тирам; на тике `t` поворачиваются только тиры, у которых `t % период == 0`;
  - проходы передачи — только по «грязному» набору: атомы, повернувшиеся на этом тике, атомы,
    у которых на этом тике изменилось кольцо, и их соседи; плюс новые / удалённые / приехавшие
    атомы, события звёзд, ЧД, перекрёстков;
  - захват у источников — только атомы рядом с источниками, у которых истёк кулдаун;
  - вращатели и бросатели — своим списком, а не проверкой в общем цикле.
- Словарь `(row,col) → атом` можно оставить, если он не узкое место по замеру; переход на
  массивы по чанкам — отдельная будущая задача (вынос ядра симуляции).
- **Проверка совпадения:** флаг отладки «полный обход» (старый путь с фиксированным
  порядком) и короткое сравнение хеша состояния через N тиков (например, 2 000) на одном и том
  же случайном поле с seed. Это проверка правильности, не нагрузочный тест — держать короткой.

### 3. Отрисовка
- Буферы MultiMesh атомов, дырок и частиц писать целиком одним вызовом на чанк
  (`RenderingServer.MultimeshSetBuffer`, как в `BlackHoleLayer`), а не поштучно.
- Обновлять только видимые чанки; неподвижное и не менявшееся — не переписывать каждый кадр,
  если это возможно без потери плавности вращения.
- Уровень детализации по зуму (пороги — настройки): при отдалении не рисовать частицы и дырки,
  атом — простая точка / кружок цвета тира; ещё дальше — можно рисовать чанк целиком одной
  заливкой по преобладающему тиру (на выбор в плане).
- Эффекты звёзд, ЧД, перекрёстков — не трогать, если по замеру они не узкое место.

## Не входит
Вынос ядра симуляции в чистый C# и массивы по чанкам, сон неподвижных линий, засыпание
зацикленных участков, многопоточность — следующие задачи. Долгие прогоны и серии замеров не
делать — проверяет пользователь.

## Итог
- Шаг 1: F3 — атомы (всего/видно), мс тика (ср./max за 1 с), тиков за кадр, мс кадра/FPS, мс отрисовки атомов.
- Шаг 2а: фиксированный порядок `CanonicalOrder` (чанк, клетка, номер создания); сначала поворот всех,
  потом вращатели; поимка летящего — по позиции на границе тика (без доли кадра).
- Шаг 2б: работа по событиям (`Touch`, `RunEventPasses`), поворот по тирам, вращатели своим списком,
  захват энергии — только атомы рядом с месторождениями. Shift+F3 — полный обход (отладка).
  Сверка: `--sim-selfcheck` (смешанное поле 4 991 атом, 2 000 тиков, хеш каждый тик — совпадает;
  поле как у T, 21 649 атомов, 500 тиков — совпадает).
- Шаг 3: буферы MultiMesh одним вызовом на слой чанка, точки на дальнем зуме, только существующие чанки.
- Замер (одно поле 13×13 чанков, 21 649 атомов, окно 1152×648): симуляция — полный обход 32,9 мс/тик,
  по событиям 4,9 мс/тик; отрисовка атомов при зуме 0,3 — 5,62 → 1,16 мс (кадр 10,1 → 6,9 мс),
  при зуме 1 — 0,69 → 0,17 мс, при зуме 0,01 — 4,25 → 0,79 мс (кадр 10,7 → 7,1 мс; чанков 3 311 → 169).
- Изменения поведения: порядок в спорных случаях (фиксирован), поимка летящего не зависит от FPS,
  T создаёт чанки только при зуме ≥ `RandomFillMinZoom`; исправлен перенос пойманного атома между
  чанками (раньше оставался в списке старого чанка — ошибки MultiMesh).
- Найдено, не исправлено: откат прибытия в клетку, которую уже занял другой атом, перезаписывает
  `_entAt` — в клетке два атома, прежний становится «невидимым» для соседей (`_detachedSet`).
